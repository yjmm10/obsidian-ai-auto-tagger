# 2026-07-20 工作日志

## 智谱 GLM 配置验证（glm-5.2 + coding 端点）
- **用户问题**：Obsidian 插件的 AI 调用报错（疑似超时 / 字段不生效），给的智谱配置为 Base URL=`https://open.bigmodel.cn/api/coding/paas/v4`、模型=`glm-5.2`、Key 已提供。
- **实测三组（curl 直连）**：
  1. 用户当前组合 coding/paas/v4 + glm-5.2：HTTP 200，但耗时 10-19s；当 max_tokens 小（16）时 content 为空、finish_reason=length（reasoning_content 占满 token）。
  2. 标准端点 paas/v4 + glm-5.2：HTTP 429「余额不足或无可用资源包」→ 说明 glm-5.2 只能走 coding 端点（用户的 coding 套餐）。
  3. 标准端点 + glm-4-flash：HTTP 200，0.76s → **Key 本身有效**。
- **结论**：端点、Key、模型名都没配错；真正问题是 **glm-5.2 是推理模型**，插件默认 `maxTokens=100` 被 reasoning 思考链占满导致真实 JSON（content）被截断 → Vercel AI SDK generateObject 解析失败 → 字段不写入；且响应 10-19s 接近默认 30s 超时。
- **验证（max_tokens=2000）**：coding 端点 + glm-5.2 正常返回 `{"tags":[...],"summary":"..."}`，finish_reason=stop。即只要给足 token 与超时即可正常工作，无需代码改造解析 reasoning_content。
- **改进**（`src/models.ts`）：① zhipu 的 note 增加「推理模型需调大最大输出 token(≥2000)与请求超时(≥60000)」提示；② BUILTIN_MODELS 增加 `glm-5.2`（标注推理模型）。`npm test` 95/0、`npm run build` 通过，已部署 main.js 到测试库。
- **用户侧修复（不改代码也行）**：设置里「最大输出 token」改 2000、「请求超时(毫秒)」改 60000，端点保持 coding/paas/v4。

## 代码默认值调整（解决超时仍触发问题）
- **问题**：用户截图显示仍报 `请求超时（30000 毫秒）`，说明设置里的 `requestTimeout` 还是 30000，没改成 60000（或旧 data.json 保留了旧值）。
- **修复**（`src/types.ts`）：把 `DEFAULT_SETTINGS.ai` 的默认值从 `maxTokens: 100 / requestTimeout: 30000` 改为 `maxTokens: 512 / requestTimeout: 60000`。这样新装/重置后不再被默认 30s 和 100 token 限制坑到。
- 说明：
  - `maxTokens` 改 512 是为了给中文 JSON 标签 + 摘要留足余量，同时避免非推理模型成本暴涨；**使用 `glm-5.2` 时仍建议手动拉到 2000**（推理思考链会占 token）。
  - `requestTimeout` 改 60000 是为了覆盖推理模型、网络波动、内容较长等场景。
- 验证：`npm run build` 通过，`npm test` 95/0，已部署 main.js 到测试库。
